### ui 关键文件

- `main.rs`：App 装配、MainTab（识别页）、OcrRow（结果行）、预览覆盖层、CSS 全在
  一个 const 字符串里（主题走 CSS 变量表）

- `tray.rs`：托盘（**别用 `TrayIcon::set_menu`，muda builder 必须 `.enabled(true)`**，
  事件挂 `use_muda_event_handler`——根因都记录在模块注释）

  `logger.rs`（运行日志：文件落盘 + 设置页查看/导出）

### 核心数据流（识别页）

```
截图/粘贴 → Frame
  → ocr_flow::recognize_raw(frame) -> (Vec<OcrLine>, ProcKind)
  → ctx.raw.set(...)                          ← 存原料（排版热重排用）
  → derive_display(&raw, kind, &opts)         ← 排版/忽略在此应用
  → finish_recognize: lines/texts/history 落地
```

#### bytes 通路逆向结论（为什么是临时文件方案）

黑盒 + 白盒双重证据，微信 4.x OCR 协议（wx4 `ParseOCRReqMessage`，request 10010）**没有 bytes 通路**：

- 黑盒判决实验：`pic_path=A图 + pic_data=B图` → 返回 **A 的内容**（带路径时 data 被无视）；
  无路径 + data + 宽高（PNG/RGBA 等多种编码）→ 请求被静默丢弃或 err=4
- 白盒（IDA 9.4 headless 反编译 `/opt/wechat-universal/libwxocr.so` 4.1.13，35MB
  stripped；方法：idat -A + IDAPython 扫立即数 + Hexrays 批量反编译；wxocr 可执行仅
  4KB 启动器，逻辑全在 libwxocr.so）：
  - 10010 处理器（`sub_2144770`）流程 = `ParseFromArray`（失败 err=2）→ **仅提取
    pic_path** → `open(path, 33)` + size（负值 **err=4**）→ read（短读 err=5）→
    解码入 OCR 管线 → 回 10011
  - **`pic_data`/`xx3`/`xx4` 从未被读取——死字段**；微信自身截图 OCR 亦无 bytes 后门
  - 坑：objdump 搜 `0x271a`（10010）撞上 AMD GPU 型号映射表（PCI 设备 ID 同值），
    先全误报；`/tmp` 落盘其实无 IO 代价（见下）
  - QQImpl（翻译源）的 `QRScanReqMessage` 截图模式（encode_pic_data+x/y，4/5/6 项）
    属于**另一个组件** WeChatUtility（返回二维码结果，非文字 OCR），不在 wxocr 内
- 工程结论（当日先行的判断，后被「零拷贝 bytes 通路」一节推翻细化）：
  `DoOCRTaskData` 的临时文件落 `$TMPDIR`，Linux `/tmp` 为 **tmpfs** →
  全程内存、零磁盘 IO；memfd/`/proc/pid/fd` 不可行（yama
  ptrace_scope=1 阻止子进程开父进程 fd），FIFO 不可行（处理器先 stat 取 size）

#### 小程序码识别（同日追加）

- **结论：现有 10010 OCR 通路即可识别小程序码**，无需新协议。响应 `qrcode[].type`：
  19=QR_CODE（普通二维码，text=解码内容）、**22=VQR_CODE（小程序码/菊花码**，
  text=引擎解出的原始载荷，跳转信息需微信服务端解析，微信自己扫码拿到的也是它）；
  条形码（EAN-13 等）数字走 `ocrResult` 文字行。两张真实样本实测通过
  （官方占位码 + 开放社区模板码）。
- 逆向佐证：libwxocr.so 内嵌改造版 zxing，存在自有扩展命名空间
  `zxing::vqrcode::{VQRCodeReader, FinderPattern, AlignmentPatternFinder…}`——
  即小程序码的完整解码器；format 名字符串表（`QR_CODE/VQR_CODE/AZTEC/…`）
  及 `BarcodeFormatFromString` 式字符串比较代码已定位（`VQR_CODE` 紧邻
  `MAXICODE`），完整枚举值表未逐项提取（19/22 已实测锚定，够用）。
- 插件落地：会话选项 `qr_mode`（仅当图中无文字时返回[默认] / 总是附加 / 不返回）；
  小程序码行加 `[小程序码]` 前缀（载荷非明文）；`score=1.0`，box 取四角点。
  样本图 `plugins/wechat_ocr/test_wxacode.png` 入仓供 ignored 测试使用。
- **顺带修掉库的上游 bug**：`XPluginManager`/`OcrManager` 把 C++ 成员变量直译成
  **类属性**（任务队列/回调表/mmojo 环境句柄跨实例共享）→ 第二个实例
  `__init__` 向满队列 `put` 直接死锁。全部改为实例属性；插件改为每次 start
  新建实例（同实例 stop 后重建 mmmojo 环境会因 ctypes 函数签名缓存冲突报
  `expected CFunctionType instead of py_object`，实测不可行）。

#### 零拷贝 bytes 通路（同日再追加：推翻「无 bytes 通路」结论）

用户的质疑是对的——**微信自己传截图不走临时文件**。深挖三层后的完整逆向
（IDA headless + objdump + 黑盒实验，wechat-universal 4.1.13）：

1. **社区三仓核查**（blueveryday/WeChatOCR = swigger wcocr.pyd 的批量套壳、
   swigger/wechat-ocr、EEEEhex/QQImpl 全量 clone）：全部只传 `pic_path`；
   swigger 注释称 bytes 传法「微信没有用到，可能为将来保留」——因为这条路
   从没被人逆向出来过。
2. **微信主程序描述符池**（`/opt/wechat-universal/wechat`，哈希表式 packed
   string table）暴露新消息 `mmremoting.ocr.protocol.ParseOCRReqSharedMessage`
   与 `WxWcdyLoadedImage`；libwxocr 的 id→名称日志表解出全家族：
   `PARSEOCR_INFO_REQ / REQ_SHARED / RESP / PARSEAI_INFO_* / GENERATE_INFO_QR_*
   / CONFIG_OCR_REQ / BENCHMARK_INFO_*`。
3. **子进程侧**：`kMMReadShared` 回调（libwxocr `0x2149030→0x2145d70`）按
   `request_id==10018` 分发到 attach 版处理器 `0x2145EF0`：
   `ParseFromArray(attach)`（元数据）→ 取宽高 → `request 缓冲区指针` 当图像
   → 视图构造 `sub_7FBF20(w,h,fmt=24,ptr)`——fmt=24 按
   `((24>>3&0x1ff)+1)×(0x28442211>>((24&7)*2)&0xf)` 展开为 **4 字节/像素
   = RGBA8888** → 进与路径版**同一个 OCR 管线** `sub_2148D80`。
4. **主程序侧发送方**（`wechat` 主程序 0x80e4b00 区，E8-rel32 扫描定位
   `GetMMMojoWriteInfoAttach` 唯一调用簇 → WriteInfo 包装类 → 10 个 sender，
   其中 OCR 的以 `mov $0x4(kMMShared), $0x2722(10018)` 构造）：
   `CreateMMMojoWriteInfo(kMMShared, sync=false, 10018, req_size=w*h*bpp,
   att_size)`——**与子进程侧完全对上**。元数据序列化器（0x80f3490）给出
   wire 布局 `{1:string, 2:varint, 3:varint, 4:submsg}`。
5. **黑盒验证**：`attach={2:W,3:H,4:rt{t1,t2}} + request=RGBA(w*h*4)` →
   **识别成功**（'GitLab Community Edition'，err=0）；三次先前失败的根因：
   字段号错位（宽高是 2/3 不是 3/4）、bytes 塞错通道（应放 request 缓冲区
   而非 pb 字段）、malformed 载荷会**打断 mojo 连接**（断连日志曾把
   "沉默"误判成"不支持"）。

**落地**：库新增 `DoOCRTaskShared(rgba, w, h)`（+ `SendBuffersWithAttach`
传输原语 + `shared_ocr_meta_pb` 手写 pb + `task_id=0` 不入队）；
插件 runBytes 优先零拷贝（PIL 解码 RGBA），无 PIL 回退 tmpfs 临时文件；
Rust 集成测试断言 runBytes 后 `/tmp` 无 `wechat_ocr_*` 残留（证明确走零拷贝）。

**协议级异步（同日再追加）**：对应 swigger `doOCR(nullptr)+wait_done` 模式——
提交即返回 + 回调按完成顺序流入 + `WaitDone` 收尾。新增 `DoOCRTasks` 批量
（队列满自动背压：注意队列放的是**空闲** id，空=全在途，满=全空闲，第一版
把方向写反了）、`PendingCount`/`WaitDone`（含 Shared 在途标记）、
`GetIdleTaskId` 修复（上游 `queue.Empty` 未接，"队列已满"分支永远不可达）。
example/5 真机验证：5 路径 + 1 Shared 穿插，6 回调全到、WaitDone 全完成。

**asyncio 门面（同日）**：库新增 `AsyncOcrManager`——`ocr_path`/
`ocr_bytes`（可并发 ≤32，以 pic_path 作关联键）、`ocr_rgba`（Shared 协议

#### 最大化调查（五轮反转，最终：自己的 CSS bug，已修复）

**最终根因**（一行）：`body{display:flex;flex-direction:row}`（Wave3 遗留）+ `#main`
未设 width → #main 作为 flex item 按内容收缩（shrink-to-fit）——窗口宽 > 内容
max-content（本机 ≈1550.640625px = 工具栏全展开的字形宽度和，LayoutUnit 1/64 精度）
时，#main 停在 1550.64，右侧 249 逻辑px 空白、标题栏按钮"消失"在收缩后的右缘。
修复 = `#main { width: 100% }`。真按钮 E2E 全通（Wayland 上最大化/还原/双击）。

**为什么追了五轮**（每轮的误判都有教训）：
1. 症状是"最大化后右侧空白+按钮点不中"，且只在窗口 >1551px（即 maximize/fullscreen）
   出现、resize（≤1550）正常——钳位数学（min(max(min-content, 可用宽), max-content)）
   让它看起来"只有最大化坏"；
2. 协议层取证（WAYLAND_DEBUG）证明 configure/buffer/damage 全对 → 排除窗口管线；
3. gdb 全线程栈证明主循环健康 → 排除死锁；
4. 像素簇 1482/1528 长期是谜——其实是按钮画在收缩后布局的右缘；"输入全灭"其实是
   按钮搬家后按旧坐标去点；
5. 外部咨询点破两个关键：1550.640625 是 LayoutUnit（1/64）值而 WebKit 真视口必为
   整数（IntSize）→ 测的是 DOM 布局不是视口；分层探针（JS 五值 + GTK allocation）
   显示 innerW/GtkWindow/vbox/webview 全部 1800 正确 → 收缩发生在 #main，是我方 CSS。

**方法论沉淀**（可复用）：
- 分层探针：`document::eval`（注意脚本被包成 AsyncFunction 函数体，**必须显式
  return**）一次拿 innerWidth/clientWidth/visualViewport/bodyW；
  tao `WindowExtUnix::gtk_window()/default_vbox()` 拿 GTK 三层 allocation——
  三分钟把嫌疑从"WebKit/tao/wry 上游"收敛到"自家 CSS"；
- shrink-to-fit 类 bug 的判别特征：坏宽度带 1/64 小数、只在窗口比内容宽时出现；
- 顺带修对的真问题：几何持久化物理/逻辑口径（下节）、`WEBKIT_DISABLE_*` 无效
  是因为渲染本来走 wl_shm。

**已撤销的临时措施**：Wayland 门控隐藏最大化按钮已移除（基于误判"上游 bug"），
maximize 在所有平台走 `set_maximized`，状态经 wry Resized 事件同步。

**单位错配教训**（适用一切 tao/wry 几何代码）：GDK 分数缩放屏上 `inner_size()`
= 物理像素（逻辑值 ×2），`outer_position()` 恒 (0,0)；曾把物理值当逻辑值写进
config 导致窗口反复以最小尺寸启动（720×520 逻辑 = 1440×1040 物理）。

#### 定位 bug 复盘（点行首数字 → 预览图无高亮）

- **现象**：识别后点行首数字，预览图不出现蓝色定位框。交互层（span onclick）、
  信号、重渲染全通——插桩日志 `[locate] click` / `[locate] view` 齐全，
  断点在 `[locate] view ... disp=(0.0,0.0) -> None`：预览图显示尺寸 img_px 恒为 0。
- **根因（异步竞态，插桩实锤）**：日志序列
  `resize evt Ok(0×0)` → `resize evt Ok(210×316)`（ResizeObserver 已送达真实尺寸）
  → `mounted rect=(0,0)`（onmounted 的 `get_client_rect` 是 evaluate_script 异步查询，
  **快照取于挂载瞬间（img 未解码=0×0）、结果晚到 ~30ms**，把真值覆盖回 0）。
  `.shot-wrap` 是 inline-block、尺寸由 img 撑开；历史上"时好时坏"= 用户先在预览图上
  按过鼠标（mousedown 重采治好 img_px）就会好，直接 OCR→点行必坏。
- **修法**：wrapper 挂 `onresize`（dioxus 内置事件，底层 ResizeObserver，事件自带
  border-box 尺寸）**唯一维护** img_px——布局定型/换图/窗口 resize 全覆盖；
  onmounted 只存挂载句柄（供 mousedown 重采）绝不写值。
- **被否证的理论**（别走回头路）：一度以为是 v2 给复制按钮加 stop_propagation
  砍掉 li 冒泡触发区——插桩证明点击从未失灵，v1"曾可用"只是 mousedown 巧合治好
  img_px 的时间相关现象；CSS 层叠/z-index 论同样不成立（修复后截图确认蓝框可见）。
- **教训**：`get_client_rect` 是异步查询，快照取于发起时刻、结果晚到——别拿它做
  "挂载后测量"，会覆盖事件驱动先到的值；要尺寸用 `onresize`。

## 环境与坑（全都踩过，直接照做）

- Bash 钩子拦截 `*.log` 后缀与 /tmp 日志路径 → 调试输出一律 `.out` 后缀
