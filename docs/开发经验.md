## 一、窗口最大化右侧空白案（五轮反转，2026-10-27）

**本项目的标志性案例**：症状极具欺骗性（"Wayland 最大化 bug"），五轮排查后真凶是
自家一行 CSS。完整时间线见 `开发记录.md`，这里只留可迁移的部分。

### 症状与误导链

最大化/全屏后窗口右侧 ~250 逻辑像素空白、标题栏按钮"消失"、点击失效；普通 resize
一切正常；`GDK_BACKEND=x11` 下"正常"（后来证明是没做渲染确认的误判）。曾先后归因于
tao/wry 上游 bug、WebKitGTK 渲染失同步、GDK 分数缩放错配——全部错误。

### 真凶

```css
body { display: flex; flex-direction: row; }  /* 布局遗留 */
/* #main（dioxus 根容器）没有 width —— 作为 flex item 按内容收缩（shrink-to-fit） */
```

窗口可用宽 ≤ 内容 max-content（本机 ≈1550.64px）时，shrink-to-fit 钳到可用宽，
一切正常；**只有最大化/全屏的窗口宽（1800）超过它**，#main 停在 1550.64，
右侧空白。修复：`#main { width: 100% }`。

### 破案的三个判据（外部咨询给出，值得背下来）

1. **WebKit 真视口必为整数**（C++ 层 `IntSize`）；测量值带 `1/64` 小数
   （如 1550.**640625** = 99241/64）说明是 **LayoutUnit 的 DOM 布局值**——测到的
   不是视口而是某个元素，且该宽度来自内容（字形宽度累加）而非窗口。
2. **高度对了就别怪缩放**：宽高共用同一个 deviceScaleFactor，若 scale 算错，
   高度不可能毫发无损。只有宽度坏 → 只影响宽度的机制（本例：收缩、扣边）。
3. **分层探针定责**，不要跳层归因：
   `document::eval` 查 `innerWidth/clientWidth/visualViewport/bodyW`（视口层）
   → tao `WindowExtUnix::gtk_window()/default_vbox()` 查三层 allocation（GTK 层）
   → 元素 rect 查 DOM 布局层。哪层数字先错，责任就在那层以下。

### 教训

- **先量 DOM，再怪上游**：四轮都假定"上游渲染坏了"，第五轮一测 innerWidth=1800
  全对，十分钟收敛到自家 CSS。
- **"X11 正常"必须做渲染确认**才能当排除证据——本例在 X11 下同样会坏，只是没人看。
- 排除法每一步都对、方向仍可能全错：协议 trace、gdb 线程栈、环境变量矩阵都真实
  排除了它们能排除的，但排除不了"根本没坏的东西"。

## 二、Dioxus 0.7 / dioxus-desktop 栈

| 坑 | 判据/现象 | 修法 |
|---|---|---|
| `get_client_rect` 异步快照竞态 | onmounted 里量到 0×0 且结果晚到，覆盖事件先到的真值 | 持续尺寸用元素 `onresize`（ResizeObserver，事件自带 border-box 尺寸）；onmounted 只存句柄 |
| `document::eval` 返回 null | 脚本被包成 AsyncFunction **函数体** | 必须显式 `return (() => ...)()` |
| rsx 渲染体内禁 `let` | `expected identifier` 编译错 | 计算挪到组件体/rsx 外 |
| `select` 无 `value` 属性 | 选中态不生效 | 每个 `option` 用 `selected: x == v` |
| Signal 是 `!Send` | 跨线程编译错 | `spawn` + `run_blocking`(onesot 回主线程) 模式 |
| muda 菜单整体灰显 | builder 的 `enabled` 是 derive(Default) bool，默认 **false** | 全部 `.enabled(true)` + 测试守卫 |
| 托盘菜单点击无动作 | dioxus-desktop 0.7.10 上游 bug：menubar/tray 的 muda handler 共用一个 OnceCell，后者注册静默失败 | handler 挂 `use_muda_event_handler`（无 menubar 时即托盘事件） |
| 托盘菜单替换后断链 | `TrayIcon::set_menu` 重建 dbusmenu，KDE 上 ItemActivated 失连 | 菜单启动建一次常驻，变化走 `MenuItem::set_text`/`set_checked` 原地刷 |
| Linux 托盘图标点击事件不存在 | tray-icon 0.21.3 GTK 后端源码只做 set_icon/menu/label | 平台差异如实文档化；Linux 用菜单项，Win/mac 用 DoubleClick；要左键唤窗需换 ksni 后端 |
| `inner_size()` 返回"错值" | Wayland 分数缩放屏上 GDK 按整数 scale（本机 2）出 buffer，返回的是**物理像素真值** | 几何持久化全程 LogicalSize（÷scale_factor）；位置 Wayland 拿不到（恒 0），不存不还原 |

## 三、GTK / KDE / Wayland 环境

- **rfd 同步对话框在 Linux GTK 后端死锁主线程** → 一律经 std 线程调（`run_blocking`）。
- **KDE Spectacle D-Bus 是 no-reply**：结果走 ScreenshotTaken/ScreenshotFailed 信号；
  portal 路径的中文文件名要 percent_decode。
- **WEBKIT_DISABLE_DMABUF_RENDERER / COMPOSITING_MODE 无效时**，先确认渲染路径：
  WAYLAND_DEBUG 里看到 `wl_shm.create_buffer` 就是软件渲染，DMABUF 变量本来就不会生效。
- **pkill 匹配自己的 wrapper 会自杀** → `pkill -x rumi-ui`；`*.log` 后缀与 /tmp 日志
  路径可能被安全钩子拦 → 用 `.out`。

## 四、架构经验（源自外部架构咨询）

1. **"为一个纯数据类型引入反向依赖"是坏味道**：ocr 对 capture 的依赖面只有 `Frame`
   一个类型 → 统一载体（`image::RgbaImage`）解耦，capture 变纯 lib，谁都好测。
2. **组合 crate 解循环依赖**：capture⇄ocr 互相需要时，新建最顶层 cli crate 同时代替
   两者链接，对外入口契约不变（bin 名与 package 名解耦：`[[bin]] name ≠ package name`）。
3. **三次法则**：重复第三次再下沉公共 crate（rumi-types），提前抽象比重复更贵。

## 五、排查方法论（按成本排序）

1. **日志先行**：交互/渲染改动必先埋 eprintln/logger，真机跑一次再下结论——
   "点行定位失灵"三轮改交互层全空转，根源在测量层。
2. **分层探针**（本手册一.3）：视口 → GTK allocation → DOM rect → 像素。
3. **像素级分析**：截图 + 暗像素聚类找字形/边界，比视觉模型稳（视觉模型整图坐标
   会漂移；裁条放大 2 倍再问可收敛）。阈值 <150-160 捕字形，<210-215 捕浅色边框。
4. **协议级取证**：`WAYLAND_DEBUG=1` 看 configure/ack/attach/damage/commit 序列，
   客户端协议对了就别再怀疑窗口管线。
5. **gdb 全线程栈**：`gdb -batch -ex run -ex "thread apply all bt" --args <bin>` 后台
   跑，SIGINT gdb 落栈（yama ptrace_scope=1 拦 attach，父进程方式不受限）。
6. **GUI 无人工验证**（KDE Wayland 实证可行）：
   - 窗口几何/激活：KWin D-Bus 脚本（`busctl --user call org.kde.KWin /Scripting
     org.kde.kwin.Scripting loadScript/start`，`workspace.windowList()`）；
   - 合成点击：ydotool 相对移动（绝对模式在 KWin 失效钉死 1,1；相对模式预热一次后
     1:1）闭环校准：读 `cursorPos` → 差值移动 → 复读修正 → `click 0xC0`；
   - 坐标标定：截图像素 ÷ 显示缩放 = 逻辑坐标。
7. **外部咨询的正确姿势**：带着实验矩阵去问，拿到判据后**立刻做判别实验**而不是
   只采纳结论——两轮咨询各给了一个判据（LayoutUnit 小数、高度正确不怪 scale），
   都是靠补测才真正破案。

## 六、多智能体协作经验（glm-flash 工人流水线）

- **规格写死一切**：API 签名、词条 key、文案、CSS 数值逐条定死，工人只执行不决策；
  规格未覆盖处要求保守实现并在回报里列出"歧义点"。
- **文件集不相交可并行**：两个工人各改各的文件，依赖按"假想 API 已存在"编码，
  合并后由门禁兜底（cargo check/test 不过自动派修复工人，有界轮次）。
- **监工必审 diff**：工人会做出规格内但体验不对的选择（如日志卡挡住状态行反馈），
  合并后人工过一遍 ambiguities 清单再收尾。
